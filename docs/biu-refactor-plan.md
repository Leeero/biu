## 1. 重构目标

### 1.1 产品目标

将 Biu 从“包含音乐播放能力的 Bilibili 内容工具”重构为“以 Bilibili 音乐内容为来源的桌面音乐播放器”。

核心用户路径调整为：

```text
发现音乐 → 开始播放 → 管理播放队列 → 收藏/下载 → 再次收听
```

### 1.2 技术目标

1. 保留并稳定现有 Electron、service、播放、下载和持久化能力。
2. 建立统一的音乐领域模型，隔离 Bilibili API 数据结构与 UI。
3. 建立可复用的 Biu 设计系统，消除页面级视觉漂移。
4. 按产品功能组织代码，逐步替换当前按页面堆叠的实现。
5. 合并收藏夹、合集和系列的重复页面逻辑。
6. 建立覆盖关键行为的自动化测试与桌面回归矩阵。
7. 保证用户已有登录态、队列、进度、设置、歌词缓存和下载记录兼容。

### 1.3 非目标

- 不更换 Electron 或迁移到 Tauri。
- 不重写现有 Bilibili 请求层。
- 不新增个性化推荐、评论、云同步等后端能力。
- 不修改现有接口请求语义。
- 不在首轮重构中引入新的状态管理框架。
- 不长期维护新旧两套 UI。

## 2. 总体策略

采用“同仓库、分阶段、纵向切片”的迁移方式：

```text
保留层
Electron / IPC / service / 核心 store
        ↓
新增层
domain / adapters / feature controllers
        ↓
重建层
ui / app shell / feature pages
        ↓
逐步删除
旧 layout / 旧 page / 重复 component
```

每个迁移批次必须完成：

1. 数据适配。
2. 新页面实现。
3. 自动化测试。
4. 人工回归。
5. 替换正式路由。
6. 删除被替代代码。

禁止只创建一个永久性的 `src/v2`，然后让两套实现长期并存。

### 4.1 层级职责

| 层级       | 职责                         | 禁止事项                       |
| ---------- | ---------------------------- | ------------------------------ |
| `service`  | 发请求、返回原始 DTO         | 不拼装页面状态                 |
| `domain`   | 定义音乐产品统一模型         | 不依赖 React 和 UI 库          |
| `adapters` | 将 API DTO 转换为领域模型    | 不直接渲染、不持有页面状态     |
| `features` | 编排用例、状态、页面和交互   | 不重复定义全局视觉规则         |
| `ui`       | 设计令牌、基础组件和页面模式 | 不调用 service 或 Electron API |
| `app`      | 路由、应用外壳和 Provider    | 不承载具体业务实现             |

## 5. 核心领域模型

重构开始前先完成最小领域模型，避免新页面继续直接依赖 Bilibili 字段。

### 5.1 Track

```ts
type TrackSource = "bilibili-video" | "bilibili-audio" | "local";

interface Track {
  id: string;
  source: TrackSource;
  title: string;
  artist?: CreatorSummary;
  cover?: string;
  duration?: number;
  quality?: "standard" | "high" | "lossless" | "dolby";
  multipart?: {
    current?: number;
    total: number;
  };
  sourceRef: {
    aid?: string;
    bvid?: string;
    cid?: string;
    sid?: number;
    localPath?: string;
  };
  capabilities: TrackCapabilities;
}
```

### 5.2 TrackCapabilities

```ts
interface TrackCapabilities {
  playable: boolean;
  canPlayNext: boolean;
  canFavorite: boolean;
  canLike: boolean;
  canTriple: boolean;
  canDownloadAudio: boolean;
  canDownloadVideo: boolean;
  canOpenSource: boolean;
  canDeleteLocalFile: boolean;
}
```

UI 根据 capability 显示操作，不再在每个页面重复判断 `bvid`、`sid`、登录态和来源类型。

### 5.3 Playlist

```ts
type PlaylistSource = "favorite" | "collected-favorite" | "collection" | "series" | "later";

interface Playlist {
  id: string;
  source: PlaylistSource;
  title: string;
  cover?: string;
  description?: string;
  creator?: CreatorSummary;
  count?: number;
  visibility?: "public" | "private";
  capabilities: PlaylistCapabilities;
}
```

### 5.4 CreatorSummary

```ts
interface CreatorSummary {
  id?: string;
  name: string;
  avatar?: string;
  followed?: boolean;
}
```

### 5.5 适配原则

- 原始 API 类型保留在 service 层。
- 页面只接收领域模型或页面 ViewModel。
- 不追求一次统一所有字段，只统一 UI 真正需要的字段。
- 无法映射的能力通过 capability 关闭，而不是伪造数据。

## 6. 设计系统计划

### 6.1 设计令牌

建立以下语义令牌：

- 背景：应用、侧栏、内容、浮层、悬停、按下。
- 文本：主文本、次文本、弱文本、禁用文本。
- 状态：品牌、成功、警告、危险、焦点。
- 边框：弱分隔、标准、强调。
- 字体：标题、正文、辅助、数字。
- 间距：4、8、12、16、20、24、32、40。
- 圆角：6、8、10、12、16、圆形。
- 动效：快速 120ms、标准 180ms、浮层 240ms。
- 层级：应用、固定播放栏、抽屉、弹窗、Toast。

### 6.2 基础组件

第一批：

- Button、IconButton。
- Tooltip。
- TextField、SearchField。
- Menu、ContextMenu。
- Dialog、Drawer、Popover。
- Tabs、SegmentedControl。
- Slider、Progress、Switch。
- Avatar、Cover、Badge。
- Empty、Loading、Error。

第二批页面模式：

- PageHeader。
- TrackRow、TrackTable。
- PlaylistCard。
- CreatorCard。
- FilterBar。
- ActionMenu。
- VirtualizedList。
- MediaGrid。

### 6.3 HeroUI 使用原则

- HeroUI 保留为交互、焦点管理和无障碍基础。
- 业务页面不直接堆叠大量 HeroUI classNames。
- 所有常用组件先经过 `src/ui` 封装。
- 不在业务页面中直接使用具体色值和随意圆角。

- 每个 adapter 有单元测试。
- 现有推荐页可通过 adapter 正常播放、收藏和下载。

## 9. 数据兼容策略

必须兼容以下已有数据：

- 登录 Cookie。

- 播放队列。

- 下载任务和记录。

规则：

1. 不直接删除或改名持久化字段。
2. 新字段提供默认值。
3. 字段变更通过带版本号的 migration 完成。
4. migration 必须幂等并有测试。
5. 升级失败时保留旧数据并回退到安全默认值。

## 10. 分支与交付策略

### 10.1 建议分支

```text
main
└── codex/biu-2-refactor
    ├── foundation/*
    ├── shell/*
    ├── player/*
    ├── discovery/*
    └── library/*
```

如团队采用短分支模式，可将阶段拆成小 PR 合入长期重构分支；不要创建一个包含全部重构的超大 PR。

### 10.2 PR 规模

- 单个 PR 尽量控制在一个领域模型、一个组件组或一个页面切片。
- 不在同一 PR 中同时修改 service 请求语义和页面视觉。
- 每个 PR 必须包含测试、迁移说明和手工验证项。

### 10.3 新旧 UI 切换

- 迁移期只在开发环境使用内部开关或临时路由。
- 页面达到退出标准后，立即替换正式路由。
- 替换完成的旧实现应在同一阶段内删除。
- 不向正式用户提供永久性“旧版/新版 UI”设置。

## 11. 风险与应对

| 风险                          | 影响 | 应对                                           |
| ----------------------------- | ---- | ---------------------------------------------- |
| 播放逻辑在 UI 重构中回归      | 高   | 播放核心先补测试，保持 store 接口兼容          |
| 新旧代码长期并存              | 高   | 每个页面切换后立即删除旧实现                   |
| 领域模型过度抽象              | 中   | 只抽象 UI 所需字段，先用推荐页验证             |
| 收藏夹类型差异被错误抹平      | 高   | 使用 capability 保留类型差异                   |
| 持久化数据无法读取            | 高   | 版本化 migration 和升级测试                    |
| Electron 安全调整破坏现有能力 | 中   | 安全加固放在功能迁移完成后逐项验证             |
| 三平台视觉和窗口行为不一致    | 中   | 每个壳层阶段执行三平台烟雾测试                 |
| UI 重构拉长开发周期           | 中   | 按可发布的纵向切片交付，不等待全部页面完成     |
| 新 PRD 暗含不存在的能力       | 高   | 所有可见操作必须通过 capability 映射到现有实现 |

2. 补齐播放队列和设置持久化测试。

## 14. 重构完成定义

只有同时满足以下条件，Biu 2.0 重构才算完成：

- PRD 中 P0、P1 功能全部迁移。
- 一级导航与新信息架构落地。
- 播放、收藏、本地音乐、下载和歌词无功能回归。
- 页面不再直接消费主要 Bilibili DTO。
- 收藏夹、合集和系列使用统一页面框架。
- 新页面只使用统一设计令牌和 UI 组件。
- 旧布局、旧页面和重复组件完成清理。
- 核心业务具有自动化测试。
- 三平台通过发布回归。
- 用户数据能够从上一正式版本无损升级。
